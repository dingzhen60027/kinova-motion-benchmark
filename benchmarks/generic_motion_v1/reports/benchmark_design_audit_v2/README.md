# Benchmark 构造文献核查与 v1 使用审计

2026-10-30；起始 HEAD `c8b91f310c77e58eabdbed466ffdd4d751be7c6f`。本次使用原 Conda 环境，只增加文献核查、输入诊断、派生注释和报告。没有新增 benchmark 规划评测，未改动题目、模型、方法参数或历史结果。

**结论：v1 的冻结输入和当前碰撞模型通过本轮检查，可用于其明确限定的受控比较；现有证据不足以把它作为覆盖广泛机械臂任务的唯一论文 benchmark。最需解决的是实际几何与名义几何的差别、场景族与端点的关联、数据分布和外部验证，而非为某个算法调整题目。** 这是一份数值审计和实验设计评估，不是零缺陷或连续安全证明。

## 1. 他人的 benchmark 是怎样构造的

检索覆盖以下十项论文工作及其作者实现/后续文档。另查 Robometrics 公开数据、OMPL 官方评测规范与 Planner Arena；它们不是额外的独立论文数据集。学术 MCP 未提供，OpenAlex 实际请求返回 HTTP 429，已改用原论文、出版页面和官方仓库；未声称完成穷尽性系统综述。

| 工作 | 已核实的构造方式 | 对当前项目最重要的区别 |
|---|---|---|
| [CSDecomp，RSS 2025](https://arxiv.org/html/2504.10783v1#S7.SS1) | Forest 随机圆障碍；FR3 桌面前20球、机器人33球近似，端点位于桌面两侧；10环境seed×10路网seed×4规模 | 400个组合不等于400个环境；表I后端统计以DRM成功为条件。当前全关节随机Kinova题与原分布不同 |
| [MotionBenchMaker，RA-L 2022](https://www.kavrakilab.org/publications/chamzas2022-motion-bench-maker.pdf) | 5机器人×8名义场景，各100题；扰动场景，位姿/IK生成端点；生成时丢弃60秒内规划器未解的题 | 适合公开结构化场景对比；成功筛题不能移植到当前无方法筛选主集 |
| [VAMP，ICRA 2024](https://www.kavrakilab.org/publications/thomason2024vamp.pdf) | 继承MBM，多个机器人；同Halton样本及边分辨率；区分原始路径和简化结果 | 不能只比较规划器名字；碰撞后端、球模型、夹爪开度与简化都影响结果 |
| [MπNets，CoRL 2022 / PMLR 2023](https://proceedings.mlr.press/v205/fishman23a/fishman23a.pdf) | 程序化tabletop/cubby/dresser；global/hybrid/both可解子集，各1800题；目标为末端位姿 | 专家成功筛选与目标修订服务学习数据；不是算法中立的固定关节端点任务 |
| [cuRobo，2023](https://arxiv.org/html/2310.17274v2) | 采用MBM/MπNets；start关节→goal位姿；60秒重启及预热，区分路径、轨迹时间和jerk | 原论文v0.6.0、后续v0.7.6与当前v0.8.0不能混用；数量与指标差异需逐项核查 |
| [GCS，2022预印本 / 2023论文实现](https://arxiv.org/html/2205.04422v1) | 固定架子与箱子中的7DoF多查询，手工IRIS seeds，PRM骨架及shortcut，单列离线构建 | 大量端点重复不增加独立环境数；应保留PRM/RRT＋shortcut强基线 |
| [pRRTC，2025预印本 / ICRA 2026](https://arxiv.org/html/2503.06757v2) | MBM多机器人，给OMPL接优化碰撞后端，同分辨率/扩展范围；报告ECDF和分位数 | 优化后的RRTConnect是正常强对照；公开代码有效输入分母仍需审计 |
| [OMPL benchmark基础设施，2015](https://moll.ai/publications/moll2015benchmarking-motion-planning-algorithms.pdf) | 固定完整问题、配置、预算、重复与日志，记录规划、简化、质量和过程 | 首解时间与持续优化时间分开，避免把失败早退误作速度优势 |
| [TrajOpt，IJRR 2014](https://rll.berkeley.edu/~sachin/papers/Schulman-IJRR2014.pdf) | 5个固定场景中布置多种构型、两两配对；198个7DoF臂问题及96个全身问题，单/多初值分开 | 不是198个独立场景；原文记录返回路径后被验证发现碰撞的失败，不能直接信solver success |
| [Clutter benchmark，ICAC 2023](https://eprints.whiterose.ac.uk/200729/1/benchmarking_of_robot_arm_motion_planning_in_cluttered_environments.pdf) | MBM式扰动，开放台面/半封闭箱/抽屉三级结构，3机器人、12规划器、参数敏感性实验 | 场景结构与端点共同构造任务；100次运行和人为难度权重不构成通用规范 |

没有一套统一的“顶会标准数值配置”。可重复的共同点是明确完整问题、场景生成与选择机制、实际几何、初始化、计算预算、独立验证和统计分母。需要保留的是这些实验原则，而不是照搬成功筛题或放宽模型的具体做法。

详细正文定位、固定仓库commit、来源SHA、未披露事项与检索失败见 [MBM/VAMP/OMPL核查](literature_mbm/research_notes.md)、[cuRobo/MπNets/GCS/pRRTC核查](literature_gpu/notes.md) 和 [补充来源记录](literature_core.json)。

本次还实际解析 Robometrics 两份公开YAML：MBM 800条题只有700种不同障碍记录，另一份MπNets有1800条和1800种不同障碍记录。精确几何不同不自动证明统计独立。它们保存末端目标和多个IK解，不能直接拼入当前固定 `q_goal` 主套件。公开代码还存在版本间目标成功谓词差异；已逐项留证据，未反推或指控原论文存在测试泄漏。

## 3. 真实样本数和独立环境

| split | 登记题数 | 合法输入 | 生成失败 | 合法短/中/长距离 |
|---|---:|---:|---:|---|
| smoke | 10 | 8 | 2 | 4/4/0 |
| dev | 60 | 60 | 0 | 20/20/20 |
| test | 420 | 395 | 25 | 158/158/79 |

test合法族分母是 sparse 95、dense 85、bottleneck 100、route_choice 95、open_control 20。25个失败来自5个完整场景，每场景5题；这些记录均在4096次提案内未找到合法起点，不能算规划失败或证明全局不可行。合法test包含75个不同随机障碍布局，加同一基础几何上的20个open任务。4个open场景ID不是4个独立物理世界，统计应合并为一个环境簇。

未发现非open场景、独立端点、无序端点对或域分离种子的精确跨split重复，也未发现按规划算法成功保留题目的规则。这不证明场景分布充分广泛。dev只有20个独立布局，每族5个；重复运行不会扩充这一数量。

短/中/长比例差异来自每场景3对和5对时循环分层的设计：dev各1/3，test为40%/40%/20%。这不是数据损坏，但原始总分反映不同混合权重，不能将dev/test均值差都解释为泛化变化。今后必须同时报告族×距离层分母及分层结果；若建立新版本，应事前固定相同目标分布，不能在v1里补换题以美化结果。dev没有open_control，后续需要额外开发对照，但不能从test搬题进dev。

## 4. 最大的环境定义问题：名义障碍与实际避障对象差别明显

当前所有方法避让的是半径0.04 m球体素并集。覆盖规则在几何上保守，但相对源障碍的膨胀较大。对1173个源球，所属覆盖球并集的最远径向外扩为3.46–5.94 cm，外接半径为源半径的1.82–2.46倍。该量是最远外边界，不是各方向均匀膨胀量或体积比例。bottleneck的名义间隙约22.1–33.6 cm，实际覆盖在间隙方向的投影间距约17.9–29.3 cm。[几何重算](local_design/sphere_cover_extent.json)

这不是只对某方法放宽碰撞模型，而是整个 benchmark 实际解决的几何问题与名义小球场景明显不同。新实测显示它会排除不少源几何下合法的构型：

| dev族 | 固定诊断构型数 | 源几何无碰撞 | 冻结球覆盖无碰撞 |
|---|---:|---:|---:|
| sparse_clutter | 640 | 456 | 303 |
| dense_clutter | 640 | 381 | 213 |
| bottleneck | 640 | 483 | 458 |
| route_choice | 640 | 503 | 459 |

`test-route_choice-011` 的128个诊断构型在源几何下有80个无碰撞，覆盖下为0；`test-dense_clutter-009` 为17对0。这说明表示效应可能参与这些场景的端点生成失败；128个样本不能证明覆盖环境无解，也不能证明它是全部失败的唯一原因。其他无合法端点场景在这批源几何样本中同样为0，仍不构成无解证明。

**当前v1应正式表述为“冻结球覆盖几何上的Kinova规划任务”。** 若希望研究原始primitive几何，必须另立版本并统一更细的表示或原生primitive接口，事前量化表示误差，不得在旧题中缩球、换端点或只为某方法改模型。

## 5. 场景标签与真正的规划困难并未等同

两堵有限大小的墙不保证路径必须穿过中间缝隙；两个障碍簇也不保证存在不同C-space同伦类别。当前端点独立地采样全7关节，因此这些名称只是workspace几何类别。辅助TCP诊断中，bottleneck仅dev 1/15、test 18/100对位于墙法向两侧；该诊断既不能证明也不能否定整个机械臂必须穿隙，但足以说明不能仅凭标签宣称“窄通道能力已测”。

新直连归因也表明，相当一部分阻塞已经来自自碰撞或固定世界：

| 合法题集合 | 直连被完整模型阻塞 | 无新增障碍也阻塞 | 新增障碍使原本可直连任务变阻塞 |
|---|---:|---:|---:|
| dev 60题 | 47 | 27 | 20 |
| test 395题 | 290 | 158 | 132 |

最后一列只表示直连二元属性的变化；对本已阻塞的任务，新增障碍仍可能进一步改变可行空间，不能说“没有影响”。test的open_control也有9/20条直连被基础模型阻塞：open表示没有新增障碍，不等于没有自碰撞、桌面或固定设备。

v1可继续用于当前随机几何分布的比较。若要研究受限通道或绕行，应在单独新套件中事前定义几何与端点关系，披露可绕行边界和通道交互的数值诊断；不能按新方法失败率来挑题，也不能把workspace标签升级成拓扑证明。

## 6. test 已经曝光，不能作为未使用的盲测

仓库中2026-10-28的24个正式运行块共有9,900条结果：9,300条合法输入运行记录，600条无效输入退出。合法输入记录中包含144条 `unsupported` 和190条 `infrastructure_error`，因此不能将全部记录称为实际进入规划算法的调用。395道合法test均已有评测记录。该事实来自运行清单与结果，不是本轮重新运行test。[曝光清点](local_design/audit.json)

v1仍可作为固定、公开、可复现的回归与比较集合；但后续在查看其结果后设计方法，不能称为未使用的holdout。仅凭曝光时序也不能指控已有结果经过test调参。若下一篇研究需要盲测泛化证据，应在方法与协议固定后另建场景独立的新版本，或锁定一个尚未用于开发的公开外部集合；须同时保留v1历史，不用新版本覆盖旧结果。

## 7. 后续实验必须固定的协议

| 维度 | v1目前可以保留 | 下一轮必须明确或补足 |
|---|---|---|
| 问题与输入 | 固定canonical模型、关节端点、球覆盖、有效输入清单 | 不把pose-goal、多IK目标与固定q_goal混成同一排行榜 |
| 数据设计 | 不按方法成功筛题；保留生成拒绝和失败 | 场景族×距离层分母；共享open环境聚类；新版本再平衡 |
| 可行性 | 合法端点与全局可行性分开 | 抽样/超时不能判无解；若另建有见证的工程集，单列选择机制 |
| 前端与后端 | 同时报告端到端和合法DRM种子后的条件结果 | RRT独立搜索与共享DRM优化器分层解释；不能只比后端或只比裸树 |
| 预算 | 现有外层60秒、方法内部配置均有记录 | 不能声称每种方法都搜索60秒；首个有效解与预算内最终质量分别报告 |
| 时间 | 离线、加载、搜索、EI-ZO、优化、简化、验证均拆分 | 新的热态实验应实际常驻并预热，不能把一次冷调用的局部计时称独立热态重复 |
| 代价 | 路径长度和有速度/加速度约束的轨迹时长分轨 | 优化器原生目标含平滑/碰撞项时需说明；成功质量用配对集合并给分母 |
| 统计 | 按场景聚类、给失败类型和共同成功配对 | 时间ECDF/分位数，避免只看成功均值；不以3个seed冒充3倍环境 |
| 数值验证 | 同模型CUDA与独立Drake，0.005 rad终检 | 是有限采样；连续保证或实机安全需要额外证据 |
| 外部有效性 | 当前Kinova随机primitive/球覆盖主集 | 单独接入公开Panda/MBM等外部轨道，审计模型和选择历史，不混合计数 |

当前优先级是：先把这些真实输入与几何属性纳入后续结果解释；再冻结新实验协议及强基线的预算；最后用另一个公开、独立任务来源检验结论。不能因为RRTConnect表现强，就把场景改得更有利于EI-ZO或未来算法。
